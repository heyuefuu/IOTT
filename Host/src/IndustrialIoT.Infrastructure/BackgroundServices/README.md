# 连接池：埃斯顿持续通信

`ConnectionPoolService` 复用设备驱动与连接。`test-connection` 成功仅表示当次协议检查成功，不代表后续通信或控制器报警已恢复。

## 埃斯顿只读保活

以下连接进入池后会自动启动独立的协议层保活任务，不依赖浏览器页面、HTTP 请求或采集任务持续运行：

- 协议为 `EstunRobot`；
- 协议为 `ModbusTCP`，品牌包含 `Estun`（不区分大小写）或 `埃斯顿`。

默认周期为 **1000 ms**。通过设备连接配置 `ExtendedProperties` 设置：

```json
{
  "KeepAliveIntervalMs": "200"
}
```

值为整数字符串，单位为毫秒，有效范围是 **51～4999 ms**；缺失、无效或超出范围时使用 1000 ms。其他品牌/协议不因这个配置启用快速保活，仍保留原有健康检查机制。

用户提供的《ER 系列工业机器人 ModBusTCP 接口调试手册（RCS2 V2.0）》2.3 节（PDF 第 7 页，正文第 6 页）明确规定：采集周期 >50 ms、响应超时 >150 ms，连接后超过 **5 秒**未收到客户端请求，服务器会自动断开并重新监听 502 端口。默认 1000 ms 为这一超时留出余量；不推荐配置接近 5000 ms 的值。

还须核实现场控制器版本和配置。周期须小于实际接收报文超时，并为请求耗时、网络延迟和调度抖动留出余量；不要未确认现场参数便修改控制器超时设置。

手册 4.2.1 节（PDF 第 20 页，正文第 19 页）说明 `40001` 的 bit0～7 循环累加、bit8 默认每 500 ms 翻转；`40252` 修改的是 bit8 信号维持时间，不是 5 秒接收超时。保活不需要写这个寄存器，也不通过写入命令区消除报警。通用 ModbusTCP 驱动的 `PingAsync` 用 FC03 读取零基地址 `0`（对应保持寄存器 `40001`），埃斯顿专用驱动则通过只读快照请求探测。

保活复用 `PingAsync` 和驱动读写锁，只发送只读请求，不发送启动、停止、复位或寄存器写入。释放连接时取消并等待保活任务结束，再关闭驱动。配置变更通过已有设备更新接口释放旧连接，下次连接时生效；不要仅修改数据库后期待已存在的连接自动刷新配置。

## 现场验证

1. 确认网页和控制器对应同一台机器人，并确认现场运行的是包含修复的 **Host 后端**；仅更新前端无效。
2. 查明控制器接收超时，确认保活周期有足够余量。Host 日志中应出现 `Device ... protocol keepalive interval: ...ms`。
3. 连接测试成功后保持页面不操作，观察超过控制器超时时间的多个周期；如有条件，用现场日志或抓包确认同一连接持续发送 Modbus 只读请求。
4. 由现场人员按照设备规程确认报警是历史记录还是持续产生的新报警。本修复不会自动复位控制器或清除报警。

保活只维护已经进入池的连接。Host 停止、设备主动释放或连接被健康检查移除后，不会由保活任务自行重新创建连接。实际掉线仍需按原有连接/采集流程恢复。慢请求或网络故障也可能使实际报文间隔超过设定周期。
